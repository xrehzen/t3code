# i18n conventions

The message catalog lives in `packages/shared/src/i18n`. This page records the
decisions behind it that a maintainer would otherwise have to infer, and the
places where getting them wrong produces broken output rather than merely ugly
output.

## Shape

`en.ts` is the canonical catalog and the source of the `MessageKey` union, so a
key is type-checked at build time and a locale catalog cannot drift from it.
Every other locale is a `Partial<Record<MessageKey, string>>`, which is what
lets a translation in progress keep compiling.

Keys are `domain.section.item`, lowercase domain, camelCase segments. Domains
are listed in the header comment of `en.ts`.

A sentence with a slot is **one interpolatable pattern**, never a prefix/suffix
pair:

```ts
"time.expiresIn": "Expires in {duration}",   // en
"time.expiresIn": "{duration} sonra dolacak", // tr
```

Turkish is SOV, so a split pair cannot produce a correct sentence: the slot
belongs somewhere else in the word order. A `{count} thread{s}` template is the
same mistake in a different guise — it renders "1 processes" in English — so
where a plural matters the keys are separate.

Where English needs a singular and plural, add both keys. Where a language does
not, one key is enough.

## Lookup and fallback

`active catalog -> en -> the key itself`. A missing key is always renderable and
never throws, so a partially translated locale degrades instead of blanking the
interface. `index.test.ts` asserts that every English key is translated in every
locale, that the interpolation slots match, and that no locale invents a key —
so an English string added without its translation fails the suite.

Catalogs are statically imported. There is no runtime JSON fetch and no dynamic
`import()`, which is what lets the Electron main process and the sandboxed
preload bundles use the same module without an async initialization step.

## Adding a locale

1. Add the catalog file with `Partial<Record<MessageKey, string>>`.
2. Register it in the `catalogs` map and in `LOCALE_PRESENTATION` (endonyms —
   someone scanning for their own language is reading an English UI).
3. Nothing else. Lookup is driven by the map, not by a conditional, so a third
   language is data rather than a code change.

## Search folding is not text folding

`foldForSearch` in `searchRanking` folds case, accents **and** the Turkish
dotted/dotless I, because a Turkish developer types ASCII even when the UI is
Turkish: without the `ı` fold, "yapilandirma" never finds "Yapılandırma".

The fold is locale-independent on purpose. The server has no locale of its own,
so a host-locale-sensitive fold would make the client and the server disagree
for the same input, which is worse than not fixing the case at all.

`normalizeSearchText` in `apps/web/src/lib/utils.ts` delegates to it. Anything
that folds text for matching should call one of the two, not reach for
`toLowerCase`.

`searchTerms` arrays are **not** translated. They are matching keys: a Turkish
user still types "settings" and "New thread", and a translated term would only
make those searches fail.

## Where a locale does not apply

`searchTerms`, product names, key names, brand names, file extensions, and any
text the user or a model authored.

Timestamps follow the **host** locale, not the interface language. A clock and
a calendar are a property of the machine, so someone on a Turkish desktop reads
"ÖS 6:00" even with an English interface. That is also why
`Sidebar.snooze.test.ts` asserting English weekday names only passes on an
English machine — the locale is an input it does not pin.

## Percentages

Turkish puts the sign before the number ("%50"), English after it ("50%"), so
percentages go through `formatPercent` rather than a template literal. The scale
factor is passed as the fraction it is: `formatPercent(0.5, locale)`.

## What lives outside the catalog

Server error text. It arrives as a flat `Schema.String` with no machine-readable
code beside it, and `apps/web/src/connection/platform.ts` parses it with
`message.toLowerCase().includes("cancel")`, so codeifying or translating it is a
contract change. The user sees a translated title with the raw provider text
underneath, which is honest about where the message came from.

Electron's own menu labels (`quit`, `copy`, `toggleDevTools`, `window`, `help`)
come from the `role:` mechanism and are localized by Chromium, not by us. They
are only translated at all because `DESKTOP_ELECTRON_LANGUAGES` keeps
`tr.pak` in the bundle — electron-builder uses that list as a pruning filter, so
without the entry the pack is deleted and no code change brings it back.
